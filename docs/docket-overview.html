The platform

Everything routes through one accountable spine: a locked case state-machine, a permission matrix, and a hash-chained audit log that every mutation passes through.

Case management

The anchor object: enforced status lifecycle (new → triaged → in progress → waiting on customer → resolved → closed/reopened), SLA policies & breach tracking, queues, categories, a full message timeline, and unguessable tracking IDs.

Agentic AI resolution

An AI agent that routes → drafts → resolves, grounded only on the curated knowledge base. Every action carries an accountability tier — autonomous, confirm, or of-record (a human must give a reasoned order) — and always offers a human handoff.

RBAC permission matrix

Seven least-privilege functional roles (super_admin → readonly) resolved through a single can? chokepoint and Pundit policies. Role grants are rank-bounded — a tenant admin can't mint a platform super-admin.

Multi-tenancy (dual topology)

One codebase, two deployment shapes: isolated (one DB per client — the sovereign procurement asset) and shared (many tenants, resolved by subdomain). Fail-closed tenant scoping; a super-admin platform console spans tenants.

An append-only, SHA-256 hash-chained log — every mutation links to the previous entry; the chain verifies end-to-end. Per-tenant filtered reads, with the global chain reserved for platform admins.

Service-Cloud parity — the five gaps closed

A focused build to reach parity-or-better against Salesforce Service Cloud on the surfaces that matter, each on existing infrastructure.

PG1routing

Declarative routing & assignment rules

Deterministic, ordered rules that classify and assign cases on intake (channel / priority / category / keyword → queue, category, priority, assignee). Rules win; the AI is the fallback. Round-robin, least-loaded, and specific-agent assignment strategies.

PG2omnichannel

Inbound omnichannel → case

Messaging channels are now two-way: a customer's WhatsApp or Telegram message opens (or threads onto) a case, and staff replies route back out the same channel. Per-provider signature verification, tenant-aware.

PG3knowledge

Knowledge-base product surface

The grounding corpus became an article product: draft/published lifecycle, internal/public visibility, slugs. A public portal KB, plus in-console article search staff can insert into a reply.

PG4approvals

Approval processes (maker-checker)

Configurable approval chains — "banks live on maker-checker." A guarded case transition (e.g. closure) or an escalated effector action parks for a checker's reasoned order before it takes effect; each approval is consumed once.

PG5MCP

MCP server face

A JSON-RPC Model Context Protocol endpoint that exposes the whole API as agent tools — auto-derived from the OpenAPI spec, re-enforcing the same auth, tenancy, and scopes. No new authority.

Security & quality

A whole-app fresh-eyes audit was run and fully resolved — 2 Critical, 4 High, 7 Medium, 12 Low, and the stray-code cleanup, each fixed with tests.

Tenant isolation

Audit, activity, security-event and CORS reads are tenant-scoped in shared mode; the global chain stays a super-admin view.

Privilege boundary

Role grants capped at the actor's own rank; over-broad policy scopes gated on read permission.

Effector safety

SSRF allowlist, fail-closed webhook HMAC, idempotency-race handling, encrypted credential vault, per-agent budgets.

Maker-checker integrity

Approvals are consumed once — repeat closures need fresh sign-off; model-driven transitions go through the gate too.

Decisioning robustness

Unique-per-(tenant,rule,subject) decisions; an overturned re-route restores the prior queue.
